A small web app where an AI agent runs inside a kernel-isolated sandbox. You watch it work, see policy denials in real time, click one button to approve a new network rule, and the rule goes live in the running sandbox. This report explains how every part works, how to run it, and how to reuse the pattern for other applications.

1The idea in one minute

Agents are useful because they can read files, call APIs and use credentials. That is also what makes them risky. OpenShell lets you run an agent with default-deny access and open up exactly what it needs, while it runs.

Problem

Agents need access, but not all of it

A research agent needs one website and one model API. It should not see your files, your keys, or the rest of your network.

OpenShell

Enforcement outside the agent

The kernel (Landlock, seccomp) and a network proxy enforce a YAML policy. The agent cannot talk its way past it, because the checks live outside its process.

This app

A human-in-the-loop console

When the sandbox blocks a request, the app shows who tried to reach what, and one click writes a minimal rule and applies it live. Then the agent retries.

The demo storyRun a task under the Strict policy → the agent tries to read Wikipedia → DENIED → click Allow this host → "policy live in N s" → Retry → the agent fetches the page, asks the model to summarise it, writes summary.md → result appears.

2Architecture: who talks to whom

Four layers. The browser talks to a small FastAPI app. The app never touches OpenShell directly; it goes through one adapter that runs the openshell CLI. The CLI talks to the gateway (control plane), which starts and governs sandboxes (data plane).

Why a CLI adapter, not the SDK?

OpenShell has a Python SDK, but it is workspace-scoped gRPC with no “policy set and wait” or “follow logs” helper. The CLI has all of it and is exactly what an operator sees. Everything funnels through openshell_client.py, so swapping to the SDK later touches one file.

Why one WebSocket?

The UI needs live events and commands (run, retry, allow, apply). One typed socket does both, and the server keeps an event log with sequence numbers, so a page reload or reconnect resumes the timeline.

Why in-memory state?

It is a demo console: one session, one sandbox. State is a list of events plus a few fields. No database, no auth. Restarting the app starts clean (and deletes leftover sandboxes).

3One task, step by step

What really happens between clicking Run and seeing the summary, including the denial and the live policy change. The diagram shows every message; the six stages below explain them in words.

The same story in words

  1. Run. The browser sends run_task. session.py checks that the provider exists, then creates a sandbox named osc-demo-xxxxxx from python:3.12-slim with policies/strict.yaml and the openrouter-agent provider attached. With the image cached this takes about a second.
  2. Upload and exec. agent.py is uploaded into the sandbox's workspace (/sandbox). Each task or retry is an openshell sandbox exec that streams the agent's stdout back line by line. The agent prints one JSON object per step: agent_start, llm_request, tool_call, tool_result, policy_denied, final.
  3. The agent is blocked. Its first tool call, fetch_url, tries to connect to Wikipedia. Under the strict policy only the model route is open, so the supervisor proxy refuses the connection. The agent sees a permission error, reports policy_denied and stops cleanly (exit code 3).
  4. The denial becomes structured data. Meanwhile the app polls openshell logs, finds the line NET:OPEN … DENIED /usr/local/bin/python3.12 → en.wikipedia.org:443, and parses out host, port and binary (section 6). The UI shows a red card with an Allow this host button.
  5. You approve. The app fetches the sandbox's base policy, adds one rule (one endpoint, one binary, read-only), writes it to a temp file and runs openshell policy set --wait. It measures the time and shows it. Network rules reload live; nothing restarts.
  6. Retry. exec runs the agent again. Now Wikipedia is allowed, the agent fetches it, calls the model through OpenRouter (the proxy swaps the placeholder for the real key), writes summary.md, and the app reads the file back into the Result panel.

4What isolates the agent, and how secrets stay secret

Four independent layers. Each one was checked on this machine.

Filesystem

Landlock

A Linux security module. Only /sandbox and /tmp are writable; system paths are read-only.

✓ proven: writing to /etc and /usr fails with PermissionError.

Syscalls

seccomp + non-root

The workload runs as uid 1000 with a syscall filter. OpenShell actively probes these kernel features before it admits the workload, and fails closed if they are missing.

✓ sandbox admitted on kernel 7.0.14-linuxkit.

Network

No direct route

The workload has no network of its own. Every connection goes through the supervisor proxy, which checks (binary, host, port) and, for HTTP, method and path.

✓ proven: unlisted hosts fail; denial is logged.

Credentials

Providers

The real key lives in the gateway. The sandbox only holds a placeholder that the proxy swaps in for one binary and one host.

✓ proven: sandbox env shows openshell:resolve:env:….

The API key never enters the sandbox

One difference from the original briefThe brief asked the agent to call inference.local. OpenShell removed that endpoint (and openshell inference) in release 0.1.0. The documented replacement, used here, is to attach a provider and call the provider's real endpoint with the placeholder key. The security property is the same; only the URL differs.

5Policies: what can change live, what cannot

A policy is a YAML file. Some parts are fixed when the sandbox starts; others can be swapped while it runs. The app is built around that split.

# policies/strict.yaml (shortened)
version: 1
# ── fixed when the sandbox starts ──
filesystem_policy:
  read_only:  [/usr, /lib, /etc, /proc, …]
  read_write: [/sandbox, /tmp, /dev/null]
landlock: { compatibility: best_effort }
process:  { run_as_user: "1000" }
# ── reloadable while running ──
network_policies: {}   # none of its own
# after “Allow this host” (merged into the base policy)
network_policies:
  allow_en_wikipedia_org:
    endpoints:
      - host: en.wikipedia.org
        port: 443
        protocol: rest        # inspect HTTP
        access: read-only     # GET/HEAD/OPTIONS
        enforcement: enforce  # block it
    binaries:
      - path: /usr/local/bin/python3.12
SectionChanges while running?Consequence in this app
network_policiesLivePresets and “Allow this host” only touch this section. Takes 3–10 s to load.
filesystem_policy, landlock, processStartup onlyStrict and Research share these blocks verbatim. Changing them means deleting and recreating the sandbox.
Provider-added rulesFrom the providerThe openrouter.ai rule comes from the attached provider, not from the policy file.

Strict

No network rules of its own. The agent can reach only the model. Any page it tries to read is denied.

Research

Adds one rule: python3.12 may GET from en.wikipedia.org, docs.python.org, example.com.

Apply edited YAML

Edit the policy in the panel and apply it. The gateway validates it; unknown fields are rejected and the error is shown in the UI.

Why presets merge instead of replacing the whole fileopenshell policy set replaces the entire policy, and OpenShell rejects removing filesystem paths on a running sandbox. So the app fetches the current base policy, swaps only network_policies, and submits that. This is also why a hand-written “Research” file could never be applied naively.

6From a denial to a rule

The whole “Allow this host” feature is three small, pure functions in app/parsing.py. They are unit-tested against output captured from the real gateway.

1 · Raw log line (real)

/usr/local/bin/python3.12(0) ->
en.wikipedia.org:443
[reason:transparent_tcp_policy_denied]

2 · parse_denials()

  host="en.wikipedia.org",
  port=443,
  binary="/usr/local/bin/python3.12",
  scope="network",
  reason="transparent_tcp_…")
→
3 · build_allow_rule() + merge_rule()
allow_en_wikipedia_org:
  endpoints: [wikipedia:443,
    rest, read-only, enforce]
  binaries: [python3.12]
→ policy set --wait

Minimal by construction

One host, one port, one binary, read-only, enforced. “Allow” never widens to wildcards or to other programs.

Guarded

The server refuses to allow a host that was not actually denied in this session, so the button cannot be abused as a generic “open anything” call.

De-duplicated

The same binary hitting the same host:port is one denial, even though the log shows several related lines.

Two things worth knowing• A sandbox with zero network rules has no proxy at all: connections just fail and no denial is logged. Strict relies on the provider's openrouter.ai rule so a proxy exists.
• Landlock (file) denials do not appear in the gateway log stream. The agent catches them and reports agent.fs_denied itself.
• OpenShell can also draft allow rules on its own (openshell rule get <sandbox> --status pending). This app uses explicit policy set because that is what was asked for and it shows the apply time.

9How to run it

Everything below was run on this Mac. Setup is already done; the first block is for a fresh machine.

Prerequisites

Docker Desktop ≥ 28

Running. Landlock needs kernel ≥ 6.2, which on a Mac means Docker's Linux VM (ours: 7.0.14).

Homebrew + Python 3.12

The installer uses Homebrew. The app uses a local .venv (no uv or pip needed on PATH).

An OpenRouter key

Free models need no credits. It lives only in .env (git-ignored) and is read by make setup.

One-time setup (fresh machine)

# 1. put your key in .env  (edit the file; do NOT re-run cp, it overwrites)
cp .env.example .env && open -e .env

# 2. pinned OpenShell v0.1.7 + gateway on Docker bridge networking
make install

# 3. venv, provider profile, provider (key → gateway), warm the image
make setup

# 4. PASS/FAIL checklist
make preflight

Every demo

make preflight     # 20 s — run this first
make run           # → http://127.0.0.1:8000

# fallback if the network or model misbehaves:
make replay        # replays a real recorded run, needs no sandbox or model

make reset         # between rehearsals: deletes demo sandboxes

3-minute talk track

  1. Open the page. “The agent runs inside a kernel sandbox. The policy on the right is what it is allowed to do.” Point at the Strict policy and the provider note.
  2. Click Run. Watch the sandbox get created in about a second and the agent start. “Its API key in here is a placeholder.”
  3. The red denial card appears. “The agent tried Wikipedia. Not allowed. We see exactly who (python3.12), what (wikipedia:443).”
  4. Click Allow this host. “One host, one binary, read-only. Applied to a running sandbox, no restart.” Point at “applied in N s”.
  5. Click Retry task. The agent fetches, calls the model, writes the file; the summary appears. Optionally click Strict to revoke the access again.

10Reliability features

preflight

make preflight

Checks CLI version vs pin, gateway, Docker, bridge networking, provider, profile, policy lint, and runs a real sandbox: creates it, confirms a strict denial, confirms the key is a placeholder, deletes it. Prints PASS/FAIL per line.

reset

make reset

Deletes every osc-demo-* sandbox and temp files. The app also does this at startup and at shutdown, and an idle timer removes forgotten sandboxes.

replay

REPLAY=1

Plays a recorded real run (denial → allow → success) with realistic timing through the same UI. No Docker, no model, no network. Record a fresh one with make record.

timeouts

Every call is bounded

Each CLI call has a timeout; a run has a generous wall-clock net (900 s). Errors from OpenShell appear in the timeline and a banner, not just in a log.

agent

No limit on tries

The agent keeps going until it finishes and retries transient model errors forever. Bad keys (401/400) fail fast, and a policy denial stops it so you can approve.

secrets

Scrubbed everywhere

All CLI output passes through a scrubber that masks the key if it ever appeared. A repo-wide scan found it nowhere except .env.

Example mappings

Coding agent

“Let an agent fix a bug in my repo”

Image with the agent CLI + git. Upload the repo to the workspace. Provider for the model API. Strict = model only; allow as needed: package registry (npm/PyPI), GitHub read-only. Show the denial when it tries npm install, approve once, retry. Result = a diff you review.

Untrusted code runner

“Run a user's script safely”

No provider, no network at all; filesystem limited to a scratch directory; resource limits (--cpu, --memory). Use --no-keep so the sandbox is deleted after the command. The console becomes a log viewer.

Data/analytics agent

“Query our warehouse, summarise”

Provider for the warehouse API with method/path-scoped rules (GET/read only); an extra provider for the model. Credentials never reach the agent's prompt or environment, so an injected prompt cannot exfiltrate them.

Tool/MCP approval

“Approve each new tool an agent wants”

Treat each new MCP/JSON-RPC server as a network endpoint; the denial card becomes an approval request. OpenShell also supports MCP/JSON-RPC-aware rules and a policy advisor where the agent proposes its own rule for you to approve.

Recipe: adapt it in six steps

  1. Pick and test the image. openshell sandbox create --from <image> -- sh. Note the user it runs as and the real path of each program that needs the network (readlink -f $(command -v node)).
  2. Write the provider profile for each API: host, port, credential env var, header, and the binary paths allowed to use it. openshell profile lint -f …, then import, then provider create --from-existing.
  3. Write the presets. Keep filesystem_policy, landlock, process identical across presets; vary only network_policies. Add them to PRESETS in session.py and to the preset buttons.
  4. Point the runner at your workload. Change the upload and the exec argv in session.run_agent(). If it does not print JSON lines, wrap its stdout lines as events.
  5. Decide how “Allow” should widen. Start with host + binary + read-only, then tighten with method/path, or loosen with a wildcard host if you must.
  6. Capture fixtures. Run a deny and an allow once, save openshell logs and policy get --base -o json into tests/fixtures, adjust the regex in parsing.py if the log shape differs, and re-record the replay.

Other ways to integrate OpenShell

12Facts, limits, and honesty notes

What was verified on this machine

✓ Strict run → denial with host, port and binary

✓ “Allow this host” applied live (6–10 s measured in the app), retry succeeded with the real model, result shown

✓ Research preset (3 hosts), Strict (revokes them), custom YAML round-trip

✓ Landlock blocks writes to /etc, /usr; the key is a placeholder in the sandbox env

✓ 26 tests, preflight, replay mode, shutdown cleanup (no sandboxes left behind)

✓ UI clicked through in a browser with the real model

Known limits & deviations

! inference.local no longer exists in 0.1.x; native endpoint used instead

! Docker Desktop needs bridge networking (host mode failed)

! Free models are slow or flaky at times; replay is the safety net

! Apply time varies 3–10 s: the sandbox polls for policy changes

! Filesystem/process changes need a new sandbox (by design in OpenShell)

! Single user, no auth, in-memory — a demo console, not a service

! The L7 (HTTP method/path) denial log shape is implemented from the docs; the verified captures are L4 connection denials

Glossary

Gateway — OpenShell's control plane (service on :17670). Sandbox — the isolated container where the agent runs. Supervisor — OpenShell process outside the agent that enforces policy and runs the proxy. Provider — a stored credential plus the rules for using it. Profile — the schema that defines a provider (hosts, binaries, env vars). Landlock — Linux kernel filesystem access control. seccomp — Linux syscall filter. OPA — the policy engine the proxy uses. OCSF — the structured event format behind the log lines.
